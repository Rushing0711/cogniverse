# 从入门到精通

## 1 模型与思考强度

Qoder CLI CN 内置国内 AI 模型，按 Credits 计费。模型选择直接影响效率、质量和成本。

### 1.1 分级模型（Default）

分级模型提供五个高性能模型池，如同智能汽车的驾驶模式：

| 级别 | 说明 | 适用场景 | Credit 倍率 |
|------|------|----------|------------|
| 智能路由 (Auto) | 智能选择最适合的模型，平衡性能与成本 | 大部分日常开发，建议默认 | ~1.0× |
| 极致 (Ultimate) | 专家级深度推理与思考能力 | 复杂系统设计、高难度问题分析 | ~1.6× |
| 性能 (Performance) | 高级推理能力，高质量输出 | 核心功能实现、架构设计、代码重构 | ~1.1× |
| 经济 (Efficient) | 标准推理能力，高性价比 | 基础代码生成、单元测试、日常问答 | ~0.3× |
| 轻量 (Lite) | 基础推理能力，免费使用 | 快速验证、基础逻辑、快问快答 | 免费 |

> **注意**：Lite 模式仅 Team 版用户可用，高峰时段可能响应较慢，且暂不支持多模态问答。

### 1.2 前沿模型（New Models）

| 模型名称 | 简介 | Credit 倍率 |
|----------|------|------------|
| Qwen3.7-Max | Agentic 能力全面跃迁，自主完成长程复杂任务 | 0.5× |
| Qwen3.7-Plus | 推理、效率与多模态体验全面跃迁 | 0.1× |
| DeepSeek-V4-Pro | 复杂推理、代码生成与工程任务表现卓越 | 0.5× |
| DeepSeek-V4-Flash | 推理速度快且成本低廉，综合能力均衡 | 0.1× |
| GLM-5.2 | 擅长复杂系统工程与长程任务 | 0.6× |
| Kimi-K2.7-Code | 专为长上下文编码打造，精准指令遵循 | 0.3× |
| MiniMax-M3 | 原生多模态感知，1M 上下文深度 | 0.2× |

### 1.3 上下文窗口

| 选项 | 说明 |
|------|------|
| 200K | 标准上下文，满足大多数任务 |
| 400K | 扩展上下文，适用于更大代码库或较长对话 |
| 1M | 最大上下文，适用于超大规模项目 |

```bash
$ qoderclicn --context-window 400000
```

TUI 中输入 `/context-window` 打开模型参数面板调整。

### 1.4 思考强度（Reasoning Effort）

控制模型生成回复前的推理深度，可用选项因模型而异：

| 选项 | 说明 |
|------|------|
| `low` | 最少推理，响应最快 |
| `medium` | 推理深度适中 |
| `high` | 深入推理，适合复杂任务 |
| `xhigh` | 深度分析，适用于高难度问题 |
| `max` | 最大推理深度，适合最复杂的挑战 |

```bash
$ qoderclicn --reasoning-effort high
```

TUI 中用 `/effort` 调整，可直接指定 level：

```
/effort high
/effort auto --session-only
/effort off
```

默认保存到 `~/.qoder-cn/settings.json`；加 `--session-only` 则仅当前会话生效。

### 1.5 Fast 模式

部分模型提供 Fast 模式，优先提升响应速度。开启后 Credit 消耗可能变化：

```
/fast on
```

### 1.6 支持参数配置的模型

Ultimate、Performance、DeepSeek-V4-Pro/Flash、Qwen3.7-Max/Plus、GLM-5.2、MiniMax-M3、Kimi-K2.7-Code 支持参数配置。其中：

- Qwen3.7-Max/Plus、GLM-5.2、MiniMax-M3 仅支持上下文窗口
- Kimi-K2.7-Code 仅支持开启 Fast 模式
- 其余同时支持上下文窗口和思考强度

### 1.7 切换模型

**TUI 中切换**：输入 `/model` 打开选择界面，分 Default、New Models、Custom 三个标签页。`↑`/`↓` 选择，`Tab` 切换标签页，`Enter` 确认，`Esc` 关闭。选择自动保存到 `~/.qoder-cn/settings.json`。

**命令行参数**：

```bash
$ qoderclicn --model efficient   # Efficient 分级
$ qoderclicn --model auto        # Auto 分级
$ qoderclicn --reasoning-effort high
$ qoderclicn --context-window 400000
```

**列出可用模型**：

```bash
$ qoderclicn --list-models
```

### 1.8 自定义模型

1. 输入 `/model`，切换到 **Custom** 标签页
2. 选择 `Add custom model...` 并按 `Enter`
3. 按引导依次选择 Provider -> 模型类型 -> 具体模型
4. 填写 API Key 等配置信息
5. 验证通过后自动保存，可立即切换使用

删除自定义模型：在 Custom 标签页选中目标模型后按 `d`。

## 2 权限与安全

### 2.1 五种权限模式

权限模式决定 Qoder CLI CN 如何处理工具调用，在「自动化程度」和「安全宽松度」两个维度定位不同：

| 模式 | 适用场景 | 行为 |
|------|----------|------|
| `default` | 常规交互式使用 | 安全读取和内部动作可自动执行；敏感操作请求确认 |
| `accept_edits` | 日常编码任务 | 自动批准工作目录内的安全文件编辑；Shell、外部动作和敏感路径仍走正常检查 |
| `auto` | 自动化运行、Goal 执行 | 零弹窗。安全读取和工作区内编辑自动批准；风险动作被拒绝或交 AI 分类器判断 |
| `bypass_permissions`（YOLO）| 仅用于可信本地实验 | 跳过所有批准提示。所有工具调用自动放行 |
| `dont_ask` | 必须不弹窗的 headless 流程 | 从不询问。任何原本需要询问的动作都会被拒绝 |

### 2.2 Plan 与 Goal 工作状态

Plan 和 Goal 是独立**工作状态**（非权限策略），可与任意权限模式共存。

**Plan 模式**：通过 `/plan` 命令进入/退出（toggle）。进入后只读探索代码并输出方案，写入受限于计划文件。退出时可选择后续权限模式或直接进入 Goal 执行。

**Goal 模式**：通过 `/goal set <目标>` 进入--自动切换到 `auto` 模式并锁定 Shift+Tab 切换，确保执行过程零打扰。Goal 可与 Plan 共存（先规划再执行）。用 `/goal clear` 或 `/goal pause` 退出。

### 2.3 模式切换

| 操作 | 说明 |
|------|------|
| `Shift+Tab` | 在所有权限模式间循环切换 |
| `Ctrl+Y` | 直达 YOLO 模式 |
| `--permission-mode <mode>` | 启动时指定默认行为 |

```bash
$ qoderclicn --permission-mode default
$ qoderclicn --permission-mode accept_edits
$ qoderclicn --permission-mode auto
$ qoderclicn --permission-mode bypass_permissions
$ qoderclicn --permission-mode yolo           # 等价于 bypass_permissions
$ qoderclicn --permission-mode dont_ask

# 快捷方式
$ qoderclicn --yolo                         # 等价于 bypass_permissions
$ qoderclicn --dangerously-skip-permissions  # 同上
```

> **注意**：非默认模式只会在可信目录中生效。如果当前目录未被信任，Qoder CLI CN 会回退到 `default`。

### 2.4 权限如何决策

每次工具调用前做权限检查。结果只有三种：`allow`（立即执行）、`ask`（需外部确认）、`deny`（阻止）。

**决策顺序**：

1. 先检查 `deny` 规则--命中即拒绝
2. 工具自身的安全检查（危险命令检测、敏感路径检测）
3. `ask` 规则--命中则标记为需确认
4. 工具级 `allow` 规则和模式带来的自动允许
5. 最终仍是 `ask`，由运行环境决定如何消费

**不同运行环境下 `ask` 的归宿**：

| 运行环境 | `ask` 的归宿 | 说明 |
|----------|--------------|------|
| TUI（交互式终端）| 弹窗确认 | 用户选择允许/拒绝 |
| Headless（`-p`）| 自动拒绝 | 无人交互，`ask` 转为 `deny` |
| SDK（stdio 协议）| 发送 `canUseTool` 回调给宿主 | 宿主决定 |
| ACP（IDE 集成）| 发送 `requestPermission` RPC 给 IDE | IDE 弹窗或自动决策 |

### 2.5 配置来源与优先级（8 层）

规则从多个来源合并，按优先级从低到高：

| 层级 | 来源 | 说明 |
|------|------|------|
| 1 | `userSettings` | `~/.qoder-cn/settings.json`（用户全局）|
| 2 | `projectSettings` | `.qoder/settings.json`（项目级，团队共享）|
| 3 | `localSettings` | `.qoder/settings.local.json`（本机个人，加 `.gitignore`）|
| 4 | `flagSettings` | `--settings` CLI 参数指定的文件 |
| 5 | `cliArg` | `--allowed-tools` / `--disallowed-tools` |
| 6 | `command` | `/allow`、`/deny` 会话中命令 |
| 7 | `session` | 运行时临时规则（弹窗"本次会话允许"）|

> **注意**：如果组织策略开启 `allowManagedPermissionRulesOnly`，则只使用策略托管的规则。`autoMode` 配置只从可信来源（用户全局 settings 和 localSettings）读取，项目 settings 被排除以防恶意权限提升。

### 2.6 模式配置

**设置默认模式**：

```json
{
  "general": {
    "defaultPermissionMode": "accept_edits"
  }
}
```

**禁用 YOLO 模式**（组织管理员）：

```json
{
  "security": {
    "disableYoloMode": true
  }
}
```

设置后，`--yolo`、`--permission-mode bypass_permissions` 和 Ctrl+Y 均不可用，Shift+Tab 循环也会跳过该模式。子 agent 声明 bypass 时会降级为 acceptEdits。

**禁用 Plan 模式**：

```json
{
  "general": {
    "plan": {
      "enabled": false
    }
  }
}
```

**Auto 模式分类器配置**--用自然语言规则引导 AI 分类器判断倾向：

```json
{
  "autoMode": {
    "allow": [
      "running npm/yarn/pnpm scripts defined in package.json",
      "creating or editing test files"
    ],
    "soft_deny": [
      "deleting files outside the test directory",
      "modifying CI/CD configuration"
    ],
    "environment": [
      "This is a Node.js monorepo with pnpm workspaces",
      "The project uses Vitest for testing"
    ]
  }
}
```

| 字段 | 作用 |
|------|------|
| `allow` | 分类器倾向于自动批准的操作描述 |
| `soft_deny` | 分类器倾向于拒绝的操作描述 |
| `environment` | 提供给分类器的环境上下文 |

> **注意**：这些规则是**软引导**--注入到分类器 prompt 作为参考，最终决策仍由 AI 分类器做出。

### 2.7 信任目录

Qoder CLI CN 将启动时的当前工作目录（CWD）视为**主信任目录**。在信任目录内：

- 文件读取默认 allow
- 文件写入在 `accept_edits` 和 `auto` 模式下可自动批准
- 非默认权限模式（auto、bypass 等）才能生效

当前目录不被信任时，强制回退到 `default` 模式。

**扩展信任范围**：

```bash
$ qoderclicn --add-dir ../shared
```

```json
{
  "permissions": {
    "additionalDirectories": ["../shared"]
  }
}
```

也可在全局 settings 配置 `permissions.trustDirectories` 永久信任常用目录。

**受保护路径**：`.git`、`.vscode`、`.idea`、`.husky`、大多数 `.qoder` 配置文件、`.bashrc`/`.zshrc` 等 shell 启动文件、Git 配置、`.mcp.json`、`.ripgreprc`。常规交互式模式需明确批准；`auto` 模式下会被拒绝。

### 2.8 权限规则配置

规则按 `allow`、`ask`、`deny` 分组：

```json
{
  "permissions": {
    "allow": [
      "Read(/src/**)",
      "Edit(/src/**)",
      "Bash(npm run test:*)"
    ],
    "ask": [
      "Bash(npm publish:*)",
      "WebFetch"
    ],
    "deny": [
      "Read(*.pem)",
      "Bash(rm -rf:*)"
    ]
  }
}
```

**规则语法**：

| 形式 | 含义 |
|------|------|
| `ToolName` | 作用于整个工具 |
| `ToolName(content)` | 作用于某个路径、命令、agent 类型或特定内容 |
| `*` | 匹配所有工具 |

规范工具名：`Read`、`Edit`、`Write`、`Bash`、`Grep`、`Glob`、`WebFetch`、`WebSearch`、`Agent`，以及 `mcp__github__create_issue` 这类 MCP 工具名。

### 2.9 文件访问规则

读取规则用 `Read(...)`，写入规则用 `Edit(...)`（覆盖 Edit、Write、NotebookEdit）。文件规则使用 gitignore 风格匹配：

| 模式 | 含义 |
|------|------|
| `/src/**` | 基于规则来源根目录的路径。project/local 相对项目根；user 相对 home |
| `~/Documents/**` | 基于 home 目录 |
| `//tmp/data/**` | 从系统 `/` 开始的绝对路径，需双斜杠 |
| `*.secret` | 不带根目录的文件名模式，任意位置匹配 |

### 2.10 Bash 规则

| 规则 | 匹配内容 |
|------|----------|
| `Bash(npm run build)` | 精确匹配 |
| `Bash(npm run test:*)` | 匹配以 `npm run test` 开头的命令 |
| `Bash(git log *)` | glob 风格通配匹配 |

> **注意**：Shell 匹配保守。`deny`/`ask` 规则会穿透常见 wrapper 和环境变量前缀；前缀和通配 `allow` 规则不会静默批准复合命令；危险命令（破坏性删除、force push）即使有宽泛 allow 也可能强制确认。`auto` 模式下危险 Shell 命令会被拒绝。除非完全信任当前会话，否则避免使用 `Bash` 或 `Bash(*)` 宽泛规则。

### 2.11 Web 和 MCP 规则

**Web**：`WebFetch(domain:example.com)` 限制抓取域名。

**MCP**：工具名格式 `mcp__<server>__<tool>`。

| 规则 | 含义 |
|------|------|
| `mcp__github__create_issue` | 单个 MCP 工具 |
| `mcp__github__*` | `github` server 下所有工具 |
| `mcp__github` | `github` server 下所有工具 |
| `mcp__*` | 所有 MCP 工具 |

仅启用指定 MCP server：

```bash
$ qoderclicn --allowed-mcp-server-names context7,github
```

## 3 基本交互（TUI）

### 3.1 启动与输入模式

在项目根目录运行 `qoderclicn` 进入 TUI。输入模式：

| 命令 | 描述 |
|------|------|
| `>` | 对话模式（默认）。输入任意文本即可对话 |
| `!` | Bash 模式。在对话模式下输入 `!` 直接运行 shell 命令 |
| `/` | 斜杠模式。打开并运行内置命令 |
| `\⏎` | 按 Enter 开始多行输入 |

### 3.2 内置工具

Qoder CLI CN 内置 Grep、Read、Write、Bash 等工具，可用于文件/目录操作和 shell 命令执行。在 TUI 中使用 `/tools` 查看当前会话可用工具。

工具能力分类：

| 类别 | 功能 |
|------|------|
| 搜索与探索 | 查找文件、搜索代码、浏览目录、Web 搜索、获取网页内容 |
| 读取项目上下文 | 查看文件、读取大文件片段、读取 PDF 等文档 |
| 编辑文件 | 修改文件、创建文件、编辑 Notebook |
| 执行命令 | 运行 shell 命令、跟踪长任务 |
| 管理上下文 | 跟踪任务、澄清问题、管理记忆、使用 Skills、规划工作 |
| 分派与自动化 | Subagents、Workflows、Goals、Worktrees、定时任务 |
| MCP 工具 | 接入外部工具和数据源 |

### 3.3 高级启动选项

| Flag | 说明 |
|------|------|
| `-w` | 指定工作区目录 |
| `-c` | 继续上次会话 |
| `-r` | 恢复指定会话 |
| `--allowed-tools` | 仅允许指定工具 |
| `--disallowed-tools` | 禁止指定工具 |
| `--max-turns` | 最大对话轮数 |
| `--yolo` | 跳过权限检查 |

### 3.4 控制工具使用

工具是否可见和是否允许执行是两件事：

| 控制项 | 说明 |
|--------|------|
| `--tools` | 限制当前会话中可见的工具 |
| `--allowed-tools` | 预先允许指定工具或工具模式 |
| `--disallowed-tools` | 阻止指定工具或工具模式 |
| `permissions.allow`/`ask`/`deny` | settings 文件中的持久化权限规则 |
| `tools.exclude` | 启动时从发现结果中移除工具 |

```bash
# 只读探索
$ qoderclicn --tools Read Grep Glob --allowed-tools 'Read,Grep,Glob'

# 允许常用状态检查命令
$ qoderclicn --allowed-tools 'Read,Grep,Bash(git status)'

# 非交互式审查中禁止文件编辑
$ qoderclicn -p "review this repository" --disallowed-tools 'Write,Edit'
```

### 3.5 好 Prompt 公式

**好 Prompt = 角色 + 目标 + 约束 + 上下文**

```
你是这个项目的核心开发者（角色）。帮我重构 src/auth 模块（目标），
保持 API 兼容（约束）。相关代码在 src/auth/*.ts（上下文）。
```

**修正方向**：

```
# Qoder 正在过度抽象
不要引入新抽象，直接用现有函数

# Qoder 正在改错文件
目标是 src/auth/，不是 src/utils/

# Qoder 漏了边界情况
考虑 token 过期和刷新的场景
```

## 4 AGENTS.md 与记忆

Qoder CLI CN 每次会话都会重新构造上下文。跨会话保留的知识来自两类记忆：`AGENTS.md`（持久指令）和自动记忆（本机 Markdown）。

> **注意**：记忆作为上下文提供给模型，但不是强制策略。需要硬性阻止某类命令、工具或路径时，请使用权限配置或 Hooks。

### 4.1 AGENTS.md 常用位置

| 位置 | 用途 | 是否适合提交 |
|------|------|--------------|
| `~/.qoder-cn/AGENTS.md` | 当前用户跨项目通用偏好和工作习惯 | 否 |
| `<project>/AGENTS.md` | 团队共享的项目规则、架构说明、常用命令 | 是 |
| `<project>/AGENTS.local.md` | 当前机器上的项目私有说明（本地服务地址等）| 否 |
| `<project>/.qoder/rules/*.md` | 按主题或文件范围拆分的项目规则 | 是 |

如需其他文件名，通过 `context.fileName` 设置单个文件名或数组。默认值是 `AGENTS.md`。

### 4.2 加载逻辑

启动或刷新记忆时，项目记忆向上查找并检查每一层的项目规则目录：

- **用户级记忆**：加载用户配置目录中的 `AGENTS.md`
- **项目和本地项目记忆**：在可信工作区内，从当前工作区目录向父目录查找 `AGENTS.md`、`AGENTS.local.md` 和 `.qoder/rules/**/*.md`，默认到 `.git` 所在目录为止
- 没有 `paths` frontmatter 的规则随项目记忆一起加载；带 `paths` 的规则按需加载
- **子目录记忆**：启动时不预加载。只有 Qoder CLI CN 成功读取子目录文件后，才从该文件所在目录向上补充未加载的记忆文件

例如在 `/repo/packages/app` 启动时，会检查：

```
/repo/packages/app/AGENTS.md
/repo/packages/app/.qoder/rules/*.md
/repo/packages/AGENTS.md
/repo/packages/.qoder/rules/*.md
/repo/AGENTS.md
/repo/.qoder/rules/*.md
```

### 4.3 规则（Rules）

规则放在 `rules/` 目录下，按主题拆分，替代单个臃肿的 `AGENTS.md`。两种作用域：

| 作用域 | 位置 | 作用范围 | 是否提交 |
|--------|------|----------|----------|
| 项目级 | `.qoder/rules/**/*.md` | 文件所在项目，团队共享 | 是 |
| 用户级 | `~/.qoder-cn/rules/**/*.md` | 每个项目，仅本机个人 | 否 |

**始终生效 vs 按路径生效**：

- 没有 `paths` frontmatter：始终生效，启动时 eager 加载
- 带 `paths` frontmatter：按路径生效，访问匹配文件后按需加载

```
---
paths:
  - src/api/**
  - "**/*.test.ts"
---

# API 规则

- 使用 `src/api/schema/` 下的共享 schema 校验请求体。
- 每个 handler 必须返回标准错误结构。
```

> **注意**：规则加载后，Qoder CLI CN 会在本次会话剩余时间里持续监视该文件。编辑规则会在下一轮被感知，无需重启。

### 4.4 自动记忆

启用后，Qoder CLI CN 在对话过程中把值得跨会话复用的信息保存为本机 Markdown 文件。

**四类内容**：

| 类型 | 用途 |
|------|------|
| `user` | 用户角色、长期偏好、跨项目工作习惯 |
| `feedback` | 用户对工作方式的纠正或确认 |
| `project` | 当前项目中无法直接从代码推导出的背景、约束或决策原因 |
| `reference` | 外部系统、看板、仪表盘、文档等资料位置 |

**启用**（仅交互式会话）：

```bash
$ QODER_MEMORY=1 qoderclicn

# 同时启用跨项目用户级自动记忆
$ QODER_MEMORY=1 QODER_MEMORY_USER=1 qoderclicn
```

**存储位置**：

```
~/.qoder-cn/projects/<project>/memory/    # 项目级
~/.qoder-cn/memory/                       # 用户级（需 QODER_MEMORY_USER）
```

每个自动记忆目录包含 `MEMORY.md` 索引和若干主题文件。`MEMORY.md` 是索引，启动时最多读取前 200 行或约 25KB。

**管理**：

```
/memory          # 打开记忆概览
/memory manage   # 管理自动记忆主题文件
```

自然语言表达：

```
记住这个项目的集成测试需要先启动本地 Redis。
忘记之前关于旧部署脚本的记忆。
把这条测试约定加到项目 AGENTS.md。
```

### 4.5 导入其他文件

`AGENTS.md` 可用 `@path/to/file` 引入其他文件。相对路径基于当前 `AGENTS.md` 所在目录解析：

```
See @README.md for the high-level architecture.
Use @docs/testing.md for test data setup.
```

- 支持相对路径、绝对路径和 `~/` 路径
- 行内代码或代码块中的 `@...` 不会被识别为导入
- 项目和本地项目记忆默认只允许导入项目边界内的文件；指向项目外的导入需显式批准

### 4.6 编写建议

把 `AGENTS.md` 当成"下次会话还要知道的事实和约定"。适合写：构建/测试/格式化/发布命令、项目目录结构、代码风格、团队工作流、长期有效的安全或合规注意事项。

不适合写：临时状态、会过期的排期、能从代码或 README 直接看出的重复内容、必须强制执行的安全策略（用权限配置或 Hooks）。

## 7 MCP 服务

### 7.1 快速开始

```bash
$ qoderclicn mcp add playwright -- npx -y @playwright/mcp@latest
```

`--` 后面的命令是 Qoder CLI CN 需要启动的服务进程。Stdio 服务随 CLI 自动启动。如果已在运行，用 `/mcp reload` 重新发现。

### 7.2 服务类型

```bash
$ qoderclicn mcp add <name> -t <type> -- <command>
```

| 类型 | 适用场景 |
|------|----------|
| `stdio` | 本地命令运行（默认）|
| `sse` | Server-Sent Events 端点 |
| `http` | HTTP 端点 |
| `ws` | WebSocket 端点 |

### 7.3 作用域

```bash
$ qoderclicn mcp add <name> -s <scope> -- <command>
```

| 作用域 | 配置文件 | 适用场景 |
|--------|----------|----------|
| `user` | `~/.qoder-cn/settings.json` | 当前账号所有项目 |
| `local` | `.qoder/settings.local.json` | 本机当前项目（默认，不提交）|
| `project` | `.mcp.json` | 随项目共享 |

### 7.4 管理服务

```bash
$ qoderclicn mcp list          # 列出已配置服务
$ qoderclicn mcp remove <name> # 移除服务
```

### 7.5 推荐服务

```bash
$ qoderclicn mcp add context7 -- npx -y @upstash/context7-mcp@latest
$ qoderclicn mcp add deepwiki -- npx -y mcp-deepwiki@latest
$ qoderclicn mcp add chrome-devtools -- npx chrome-devtools-mcp@latest
```

### 7.6 MCP 权限

MCP 工具仍经过权限系统。工具名格式 `mcp__<server>__<tool>`。默认模式调用 MCP 工具通常请求确认。可批准具体工具、批准某 server 下所有工具，或在 settings 配置规则：

```json
{
  "permissions": {
    "allow": ["mcp__context7__*"],
    "deny": []
  }
}
```

### 7.7 故障排查

- 运行 `qoderclicn mcp list` 确认服务已配置
- 已在运行时，添加或修改服务后执行 `/mcp reload`
- 确认 `--` 后面的命令可在终端正常运行
- 基于 `npx` 的服务确认 Node.js 和网络可用
- 服务已连接但工具调用被阻止，检查权限提示

## 8 Subagent 子代理

Subagent 是专门处理某类任务的 Agent，拥有独立的对话上下文、系统提示词、工具集合、模型配置、权限模式和运行限制。

### 8.1 内置 Subagent

| 名称 | 能力 |
|------|------|
| `general-purpose` | 通用研究型。复杂搜索、多文件分析、调用链追踪。未指定类型时默认使用 |
| `Explore` | 快速只读代码探索。查找文件、搜索符号、理解实现 |
| `Plan` | 只读方案设计。改代码前梳理实现路径、关键文件、依赖顺序 |
| `qoder-guide` | 回答 Qoder CLI CN 使用、配置、Skills、Agents 等问题（非 SDK 模式）|
| `statusline-setup` | 配置自定义 status line（TUI 模式）|
| `SaveMemory` | 管理跨会话记忆、偏好和事实（记忆能力启用时）|

### 8.2 来源和优先级

同名定义按优先级覆盖，从低到高：

| 优先级 | 来源 | 入口 |
|--------|------|------|
| 1 | Built-in | `/agents` 的 BuiltIn 标签页 |
| 2 | User | `~/.qoder-cn/agents/*.md` |
| 3 | Project | `.qoder/agents/*.md` |
| 4 | Plugin | 已安装插件提供 |
| 5 | Flag | `--agents` JSON（最高优先级）|

被覆盖的定义在 `qoderclicn agents list` 中标记为 `shadowed`。

### 8.3 创建自定义 Subagent

**方式一：AI 辅助生成（推荐）**

1. TUI 中执行 `/agents`
2. `Tab` 切换到 User 或 Project 标签页
3. 选择 `Create new agent...` 并按 `Enter`
4. 输入 Subagent 描述并确认

生成后保存在 `.qoder/agents/`（项目级）或 `~/.qoder-cn/agents/`（用户级）。

**方式二：手动编写配置（进阶）**

```
---
name: api-reviewer
description: Review API designs, endpoint naming, request methods, status codes, error responses, and versioning.
tools: [Read, Grep, Glob]
disallowedTools: [Write, Edit]
permissionMode: default
model: inherit
maxTurns: 8
timeoutMins: 10
color: cyan
---

You are an API design reviewer.

Focus on:
- Resource naming and URL structure
- Request method semantics
- Status code and error response consistency

Return concise findings grouped by severity.
```

需要独立 worktree 执行时，加 `isolation: worktree`。文件名不决定名称，名称来自 frontmatter 的 `name` 字段。

### 8.4 配置字段全表

| 字段 | 必需 | 可取值 | 含义 |
|------|------|--------|------|
| `name` | 是 | 非空字符串 | Subagent 名称 |
| `description` | 是 | 非空字符串 | 用途说明，影响调度 |
| `background` | 否 | 布尔值 | 是否默认后台运行 |
| `color` | 否 | red/blue/green/yellow/purple/orange/pink/cyan | TUI 展示颜色 |
| `disallowedTools` | 否 | 字符串或数组 | 工具黑名单 |
| `effort` | 否 | low/medium/high/xhigh/max 或正整数 | 推理强度 |
| `hooks` | 否 | Hook 配置对象 | 仅作用于该 Subagent |
| `initialPrompt` | 否 | 字符串 | `--agent` 作为主 Agent 时的初始提示 |
| `isolation` | 否 | worktree | 隔离方式 |
| `kind` | 否 | local/remote | 类型 |
| `maxTurns` | 否 | 正整数 | 最大对话轮次 |
| `mcpServers` | 否 | 服务名数组/内联对象 | 额外 MCP 工具 |
| `memory` | 否 | user/project/local | 持久记忆作用域 |
| `model` | 否 | 模型名或别名 | 模型，省略为 inherit |
| `permissionMode` | 否 | default/acceptEdits/bypassPermissions/dontAsk/auto/plan | 权限模式 |
| `skills` | 否 | 字符串或数组 | 限制可用的 Skills |
| `temperature` | 否 | 数字 | 模型温度 |
| `timeoutMins` | 否 | 正整数 | 最长执行时间（分钟）|
| `tools` | 否 | 字符串或数组，支持 `*` | 工具白名单 |

### 8.5 调用方式

**显式调用**：

```
使用 api-reviewer subagent 审查这个接口设计
@api-reviewer 审查这个接口设计，只返回需要修改的点
```

**隐式调用**：自然语言输入任务，Qoder CLI CN 根据 `description` 自动选择。

**作为会话主 Agent**：

```bash
$ qoderclicn --agent api-reviewer
$ qoderclicn --agent api-reviewer -p "审查这个接口设计"
```

**`--agents` 临时注入**：

```bash
$ qoderclicn \
  --agents '{"api-reviewer":{"description":"Review API designs","prompt":"You are an API reviewer.","tools":["Read","Grep","Glob"],"maxTurns":6}}' \
  -p "使用 api-reviewer subagent 审查 docs/api.yaml"
```

### 8.6 编排多个 Subagent

```
先使用 general-purpose subagent 检查实现方案，再使用 api-reviewer subagent 审查 API 设计
```

彼此独立的任务可并行调度；有依赖关系说明先后顺序。`--max-turns` 是 Headless 查询的总轮次上限。

### 8.7 权限继承

- 未声明 `permissionMode` 时，继承父会话当前模式
- 父会话处于 `acceptEdits`/`bypassPermissions`/`auto` 时，Subagent 不能通过自己的配置降得更严格
- `plan` 不污染主会话计划状态，只在隔离上下文生效

## 9 Skills 技能

Skill 将专业知识打包成可复用功能，每个 Skill 包含 `SKILL.md`（描述、指令）和可选辅助文件。

### 9.1 工作原理

- 启动时加载每个 Skill 的名称和描述，保持快速启动
- 请求与 Skill 描述匹配时，模型请求使用该 Skill 并加载完整 `SKILL.md`
- 按指令执行，按需加载引用文件或运行脚本

### 9.2 存储位置

| 位置 | 路径 | 作用域 |
|------|------|--------|
| 用户级 | `~/.qoder-cn/skills/{skill-name}/SKILL.md` | 当前用户所有项目 |
| 项目级 | `.qoder/skills/{skill-name}/SKILL.md` | 仅当前项目 |

同名时项目级覆盖用户级。

### 9.3 Skill vs Command

| 特性 | Skill | Command |
|------|-------|---------|
| 触发方式 | 模型自动判断或 `/skill-name` | `/command-name` |
| 主要用途 | 专业领域知识、复杂工作流 | 快速执行预设任务 |
| 存储位置 | `skills/` 目录 | `commands/` 目录 |
| 权限确认 | 视能力而定，可能需授权 | 不需要 |

> **注意**：Skill 内部转换为特殊类型的 Command，两者共享执行机制。

### 9.4 创建 Skill

```
{skill-name}/
├── SKILL.md          # 必需：主文件
├── REFERENCE.md      # 可选：详细参考
├── EXAMPLES.md       # 可选：示例
├── scripts/          # 可选：辅助脚本
└── templates/        # 可选：模板
```

`SKILL.md` 格式：

```
---
name: skill-name
description: Skill 功能简述，说明何时使用
---

# Skill Name

## Instructions
提供清晰的分步指导。
```

**Frontmatter 字段**：

| 字段 | 必需 | 说明 | 限制 |
|------|------|------|------|
| `name` | 是 | 唯一标识 | 小写字母、数字、连字符，最多 64 字符 |
| `description` | 是 | 功能描述，模型据此判断何时使用 | 最多 1024 字符 |

> **注意**：`description` 决定模型何时使用 Skill，应包含功能说明和使用时机。

### 9.5 使用与刷新

```
/skills              # 管理当前工作区 Skill
/skills reload       # 刷新已发现的 Skill
/skill-name          # 手动触发
```

直接描述需求让模型自动判断：

```
分析这个日志文件中的错误
```

### 9.6 最佳实践

- 每个 Skill 专注一个领域或任务类型
- `description` 包含功能、使用时机和触发关键词
- 共享前确保预期场景能触发、指令清晰、覆盖边界情况
- 记录版本变更

## 10 Hooks 钩子

Hooks 允许在 Qoder CLI CN 关键节点接入 Agent 主执行流，与 CLI 解耦。常见用途：工具执行前拦截危险操作、任务完成后发桌面通知、写文件后自动跑 lint。

### 10.1 配置文件位置

三级配置被合并执行：

```
~/.qoder-cn/settings.json          # 用户级，对所有项目生效
${project}/.qoder/settings.json    # 项目级，可提交 git
${project}/.qoder/settings.local.json  # 项目级本地，优先级最高
```

### 10.2 配置格式

```json
{
  "hooks": {
    "事件名": [
      {
        "matcher": "匹配条件",
        "hooks": [
          {
            "type": "command",
            "command": "要执行的命令",
            "timeout": 60
          }
        ]
      }
    ]
  }
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `type` | 是 | 固定 `"command"` |
| `command` | 是 | 要执行的 shell 命令 |
| `timeout` | 否 | 超时秒数，默认 60 |
| `matcher` | 否 | 匹配条件，不填匹配所有 |

### 10.3 matcher 匹配规则

| 写法 | 含义 | 示例 |
|------|------|------|
| 不填或 `"*"` | 匹配所有 | 所有工具都触发 |
| 精确值 | 精确匹配 | `"Bash"` 只匹配 Bash |
| `\|` 分隔 | 匹配多个值 | `"Write\|Edit"` |
| 正则表达式 | 正则匹配 | `"mcp__.*"` 匹配所有 MCP 工具 |

### 10.4 Hook 脚本输入输出

**输入**（stdin JSON）：

| 字段 | 说明 |
|------|------|
| `session_id` | 当前会话 ID |
| `cwd` | 当前工作目录 |
| `hook_event_name` | 触发的事件名称 |

不同事件附加额外字段。

**输出**（exit code + stdout）：

- exit 0：成功，stdout JSON 可为部分事件提供精细控制
- exit 2：阻塞（stderr 内容注入对话，仅对支持阻塞的事件生效）
- 其他：非阻塞错误

**环境变量**：

| 变量 | 说明 |
|------|------|
| `QODER_PROJECT_DIR` | 当前项目工作目录 |

### 10.5 支持的事件

| 事件 | 触发时机 | matcher 匹配 |
|------|----------|-------------|
| `SessionStart` | 会话开始 | 会话来源：startup/resume/compact |
| `SessionEnd` | 会话结束 | 结束原因：prompt_input_exit/other |
| `UserPromptSubmit` | 用户提交 Prompt 后、Agent 处理前 | - |
| `PreToolUse` | 工具执行前（可阻止）| 工具名 |
| `PostToolUse` | 工具执行成功后 | 工具名 |
| `PostToolUseFailure` | 工具执行失败后 | 工具名 |
| `Stop` | 主 Agent 完成响应（可阻止停止）| - |
| `SubagentStart`/`SubagentStop` | 子 Agent 启动/完成 | Agent 类型名 |
| `PreCompact` | 上下文压缩前 | 触发方式：manual/auto |
| `Notification` | 通知触发（权限请求、任务完成）| 通知类型：permission/result |
| `PermissionRequest` | 权限管道产出 `ask` 后、弹窗前 | 工具名 |

### 10.6 Hook 与权限

Hook 系统在权限决策链路有两个注入点：

| 事件 | 触发时机 | 权限影响 |
|------|----------|----------|
| `PreToolUse` | 工具执行前 | 可返回 `permissionDecision: allow/deny/ask` 覆盖权限管道 |
| `PermissionRequest` | 权限管道产出 `ask` 后、弹窗前 | 可返回 `decision.behavior: allow/deny` 代替用户交互 |

> **注意**：Hook 的权限决策优先级**高于**权限模式--即使在 `bypass_permissions` 模式下，PreToolUse Hook 返回 `deny` 仍然会阻止执行。这为组织级安全策略提供了不可绕过的拦截能力。

**执行顺序**：

1. Hook `PreToolUse` -> 如果返回 allow/deny，短路
2. 权限管道（规则 + 模式 + 安全检查）
3. 如果结果是 `ask` -> Hook `PermissionRequest` -> 如果返回 allow/deny，短路
4. 最终由运行环境消费 `ask`

### 10.7 实战示例

**拦截危险命令**（PreToolUse + Bash）：

```bash
#!/bin/bash
input=$(cat)
command=$(echo "$input" | jq -r '.tool_input.command')
if echo "$command" | grep -q 'rm -rf'; then
  echo "危险命令已被阻止: $command" >&2
  exit 2
fi
exit 0
```

**写文件后自动 Lint**（PostToolUse + `Write|Edit`）：

```bash
#!/bin/bash
input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path')
case "$file_path" in
  *.js|*.ts|*.jsx|*.tsx) npx eslint "$file_path" --fix 2>/dev/null ;;
esac
exit 0
```

**让 Agent 继续工作**（Stop）：

```bash
#!/bin/bash
if [ -n "$(git status --porcelain 2>/dev/null)" ]; then
  echo "检测到未提交的变更，请完成 git commit" >&2
  exit 2
fi
exit 0
```

## 11 Plugins 插件

Plugin 将命令、子 Agent、Skill、Hook、MCP server 等打包成一个目录，便于安装、启用与共享。

### 11.1 插件目录结构

```
my-plugin/
├── .qoder-plugin/
│   └── plugin.json        # manifest（name/version 等元信息）
├── commands/              # 自定义命令
├── agents/                # 自定义子 Agent
├── skills/                # 自定义 Skill
├── hooks/
│   └── hooks.json         # Hook 配置（包裹格式）
├── output-styles/         # 输出样式
├── bin/                   # 可执行文件
└── .mcp.json              # MCP server 声明
```

### 11.2 manifest 字段

`plugin.json` 仅 `name` 必填：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 唯一标识，kebab-case |
| `version` | 否 | 语义化版本号 |
| `description` | 否 | 简短描述 |
| `author` | 否 | 作者信息 |
| `homepage` | 否 | 文档/主页 URL |
| `repository` | 否 | 源码仓库 URL |
| `license` | 否 | SPDX license 标识 |
| `keywords` | 否 | 标签数组 |

### 11.3 安装作用域

| 作用域 | 说明 | 适用场景 |
|--------|------|----------|
| `user` | 全局可用，所有项目（默认）| 个人常用插件 |
| `project` | 当前项目，可提交 git | 团队共享 |
| `local` | 当前项目，写入 local.json | 本地实验 |

### 11.4 命令

```bash
$ qoderclicn plugins install ~/my-plugin              # 安装
$ qoderclicn plugins install /abs/path --scope project
$ qoderclicn plugins uninstall my-plugin              # 卸载（别名 remove/rm）
$ qoderclicn plugins enable my-plugin                 # 启用
$ qoderclicn plugins disable my-plugin                # 禁用
$ qoderclicn plugins disable --all                    # 一键禁用
$ qoderclicn plugins list                             # 列出
$ qoderclicn plugins list --json
$ qoderclicn plugins validate ~/my-plugin             # 校验
```

### 11.5 enabledPlugins 配置

```json
{
  "enabledPlugins": {
    "my-plugin@local": true,
    "another-plugin@local": false
  }
}
```

值为 `true` 启用，`false` 显式禁用。配置 key 必须与已安装插件 ID 完全匹配（本地安装形如 `name@local`）。

### 11.6 插件 Hook 编写

插件在 `hooks/hooks.json` 声明 Hook，使用**包裹格式**（外层多一层 `{ "hooks": ... }`）：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"${QODER_PLUGIN_ROOT}\"/scripts/check.sh"
          }
        ]
      }
    ]
  }
}
```

插件 Hook 执行时额外得到环境变量：

| 环境变量 | 说明 |
|----------|------|
| `QODER_PLUGIN_ROOT` | 插件安装根目录 |
| `QODER_PLUGIN_DATA` | 插件数据目录（跨升级保留状态）|

> **注意**：插件提供的 Subagent 会应用额外安全策略：`hooks`、`mcpServers`、`permissionMode` 会被移除，`isolation` 只有 `worktree` 会被保留。

## 12 动态工作流

动态工作流让 Qoder CLI CN 在后台运行结构化的多 Agent 流程，适合分阶段执行、大规模并发、交叉验证或复用固定流程的任务。

### 12.1 何时使用

| 方式 | 适合场景 |
|------|----------|
| Subagent | 单个聚焦子任务，只需总结返回主会话 |
| Skill | 可复用的说明、领域知识或流程 |
| 动态工作流 | 多个子 Agent、多个阶段、并行分支或验证轮次 |

适合：仓库审计、深度研究、迁移规划、发版检查、跨文件扫描、需多视角汇总的评审。

### 12.2 运行

```
使用动态工作流审查这个仓库的安全风险，并总结发现。
使用 deep-research 动态工作流调研这个架构决策的取舍。
```

也可按名称调用已保存的工作流。动态工作流作为后台任务运行，启动后返回运行 ID，在 `/workflows` 面板持续展示进度。

### 12.3 保存位置

| 范围 | 位置 | 场景 |
|------|------|------|
| 项目级 | `.qoder/workflows` | 属于当前仓库或团队 |
| 用户级 | `~/.qoder-cn/workflows` | 跨项目个人工作流 |
| Plugin | Plugin 提供 | 随插件分发 |
| 内置 | Qoder CLI CN 内置 | 官方提供 |

名称冲突时，项目级优先级高于插件级和内置。

### 12.4 工作流脚本

保存的工作流是以 `meta` 导出对象开头的 JavaScript 文件：

```javascript
export const meta = {
  name: "repo-audit",
  description: "Audit a repository area and summarize risks",
  whenToUse: "Use when the user asks for a structured repository audit",
  phases: [
    { title: "Scan", detail: "Find relevant files and areas" },
    { title: "Analyze", detail: "Run focused analysis agents" },
    { title: "Summarize", detail: "Merge findings into a final report" }
  ]
};
```

脚本可用辅助函数：`agent()`、`parallel()`、`pipeline()`、`phase()`、`log()`、`workflow()`、`args`、`budget`。

### 12.5 运行机制

1. Qoder CLI CN 为任务选择已保存工作流或创建新的
2. 需要审查时展示名称、阶段、脚本和运行选项
3. 作为后台任务启动
4. 脚本启动子 Agent 并归入不同阶段
5. 中间结果保存在运行时，不填满主会话上下文
6. 最终结果写入运行输出，回到当前会话总结

> **注意**：动态工作流脚本不能直接访问 shell、文件系统、网络、Node.js API 或 MCP 服务。所有副作用通过子 Agent 发生，子 Agent 仍经过工具、权限、Hooks 和沙箱设置。

## 13 Remote Control 与云端模式

### 13.1 Remote Control 远程控制模式

两种模式：

**远程控制模式**（本地任务远程控制）：已在电脑上启动 CLI 会话，临时离开但想继续监控。

```
/remote-control           # 开启远程监听，显示二维码和 URL
/remote-control stop      # 停止
/remote-control status    # 查看连接状态
```

用手机扫码或浏览器打开 URL 连接，可实时查看状态、审批操作、从移动端发送新任务。需保持本地电脑活跃。

**守护进程模式**（手机端直接发起任务）：电脑保持待命，随时通过手机发起新任务。

```bash
$ qoderclicn remote-control    # 启动守护进程
```

显示二维码和 URL，手机连接后可发多个任务。按 `Ctrl+C` 退出。需保持本地电脑活跃。

### 13.2 云端模式（--remote）

`--remote` 让任务直接在 Qoder 管理的云端 VM 执行，本地电脑无需保持开机或活跃。

**适用场景**：长时任务、离线发起、统一环境、资源隔离。

```bash
$ qoderclicn --remote "review the auth middleware in src/middleware and suggest improvements"
```

执行后：在云端创建会话 -> 发送任务 -> 实时流式打印输出 -> 完成后打印会话 URL。任务发起后即使关闭本地终端，云端 Agent 仍继续执行。

**选择云端环境**：

```
/remote-env
```

选定后写入 `~/.qoder-cn/settings.json`：

```json
{
  "remote": {
    "defaultCloudEnvironmentId": "env_xxx"
  }
}
```

### 13.3 两者对比

| 维度 | Remote Control | 云端模式 |
|------|----------------|----------|
| 执行位置 | 本地电脑 | 云端 VM |
| 本地电脑 | 需保持活跃 | 无需开机 |
| 任务发起 | 手机/Web | CLI/手机 |
| 上下文 | 本地工作目录 | 云端环境对应 GitHub 项目 |
| 中断行为 | 停止远程控制 | `Ctrl+C` 仅断开订阅，云端任务继续 |

## 14 安全扫描

### 14.1 三个扫描级别

| 级别 | 面向 | 说明 | 计费 |
|------|------|------|------|
| L1 Static Check | 当前任务生成的代码 | 高风险模式匹配，检查危险函数调用、敏感信息泄露 | 免费 |
| L2 Lightweight Scan | 增量代码变更 | 理解代码语义，识别 SQL 注入、远程命令执行等 | 可能消耗 Credits |
| L3 Deep Scan | 增量代码变更 | 跨文件、跨函数追踪完整数据流 | 可能消耗 Credits |

> **注意**：安全扫描不是替代安全团队审计的完整方案，主要面向当前任务生成的代码和增量变更。

### 14.2 配置

TUI 中输入 `/security-settings` 打开设置面板，`↑`/`↓` 移动，`Enter`/`Space` 切换开关，`q`/`Esc` 退出。

或用户级 settings.json：

```json
{
  "securityScan": {
    "l1StaticCheck": true,
    "l2LightweightScan": true,
    "l3DeepScan": true
  }
}
```

三个默认都是 `true`。L1、L2、L3 全部关闭时，安全扫描能力不会加载。

### 14.3 手动安全扫描

```
/security-scan
```

打开选择器，选项包括 L3 深度扫描、L2 轻量扫描、项目/文件扫描。也可直接写明：

```
/security-scan L2 轻量审查
/security-scan L3 深度审查
/security-scan 扫描整个仓库
/security-scan 扫描 src/auth 和 src/export
```

### 14.4 使用场景

- Qoder CLI CN 生成或修改安全敏感代码后（鉴权、支付、数据导出、文件上传、命令执行）
- 提交代码或交付前快速检查
- 评审前得到面向真实漏洞的风险提示
- 自动化模式中保留持续安全检查

## 15 Worktree 工作树

使用 `--worktree [name]` 在独立 Git worktree 中启动会话，适合同一仓库并行处理多个任务。

> **注意**：要求在 Git 仓库中运行，并确保本地已安装 Git。

```bash
$ qoderclicn --worktree feature-a
$ qoderclicn --worktree feature-a "Implement the login fix"
$ qoderclicn --worktree          # 不传名称，自动生成
```

worktree 准备完成后切换到该 worktree 启动会话。会话结束时打印 worktree 路径和恢复命令：

```
cd <worktree-path> && qoderclicn --resume <session-id>
```

手动删除 worktree：

```bash
$ git worktree remove <worktree-path>
```

## 16 自定义命令

### 16.1 命令配置格式

Prompt 类型自定义命令为 Markdown 文件，包含 frontmatter 元数据和系统提示词：

```
---
name: git-commit
description: Use this command when you need to review all git changes and generate a well-structured commit message.
---

You are an expert Git commit message generator. Your role is to analyze all git changes in the repository and create clear, concise, and meaningful commit messages.
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 命令唯一名称，用于 `/command-name` 调用 |
| `description` | 是 | 功能描述，支持多行（YAML 语法）|

### 16.2 命名规范

- 使用小写字母和连字符（如 `git-commit`）
- 避免空格或特殊字符
- 文件名与 `name` 字段保持一致
- 子目录用 `:` 作为命名空间分隔符，如 `commands/git/commit.md` 注册为 `/git:commit`
- 同目录下若存在 `SKILL.md`，该目录注册为单个命令，其它兄弟 `.md` 文件被忽略

### 16.3 存储位置与优先级

| 级别 | 路径 | 生效范围 | 是否提交 |
|------|------|----------|----------|
| 项目级 | `.qoder/commands/<name>.md` | 仅当前项目 | 建议提交 |
| 用户级 | `~/.qoder-cn/commands/<name>.md` | 所有项目 | 不提交 |

项目级优先于用户级。新增或修改后运行 `/commands` 重新加载。

### 16.4 AI 辅助生成

1. TUI 中执行 `/commands` 进入配置面板
2. `Tab` 切换到 User 或 Project 标签页
3. 选择 `Create new command...` 并按 `Enter`
4. 描述期望创建的命令功能
5. 自动生成配置文件并保存到对应目录
